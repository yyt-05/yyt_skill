# Finding 严重级别与审查输出

## 严重级别

- **P0：** 已发生或极可能发生的灾难性问题，例如严重数据破坏、凭据泄露、未经授权生产动作或系统大面积不可用；必须立即阻止发布。
- **P1：** 在正常或可信场景下会造成主要功能错误、安全边界破坏、不可恢复状态或发布失败；合并前必须修复。
- **P2：** 在特定但合理场景下造成错误结果、兼容性问题、明显性能/运维风险；通常应在合并前修复或明确接受。
- **P3：** 低风险但具体可复现的可维护性、诊断性或局部质量问题；不应阻塞核心交付。

严重级别由影响、可达性、发生概率和恢复成本共同决定，不能只看代码行数。

## Finding 格式

```markdown
### [P1] <动作化标题>

位置：`path/file.py:123`

当 <具体输入/时序/环境> 时，<代码行为>，导致 <用户或系统影响>。当前的 <测试/保护> 未覆盖，因为 <证据>。建议最小修复方向：<方向，不展开无关重构>。
```

保持行号范围最小。问题跨文件时，以错误发生或最适合修复的位置为主，并在正文引用必要调用方。

## 不应提交的 Finding

- 纯样式偏好，且仓库规范没有要求；
- 与当前 diff 无因果关系的历史问题；
- 没有具体触发场景的“可能出错”；
- 仅建议增加防御代码，但输入契约保证该情况不可能发生；
- 要求为未知调用方保留兼容，却没有调用证据；
- 将“测试可以更多”作为 finding，却说不清缺失测试会漏掉什么风险；
- 重复报告同一根因的多个表面症状。

## 推荐输出结构

```markdown
## Findings

1. [P1] ...
2. [P2] ...

## 未验证范围

- <未运行检查、不可访问环境或未知外部契约>

## 结论

保持 Draft / 暂不合并 / 修复后可合并 / 当前证据下可合并。
```

没有 finding 时使用：

```markdown
未发现需要阻塞合并的问题。

未验证范围：<如有>。
残余风险：<如有>。
```

不要为了显得审查充分而制造低价值问题。
