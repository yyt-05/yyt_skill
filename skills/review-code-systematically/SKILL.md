# 系统化代码审查

代码审查的目标不是复述作者意图或寻找格式问题，而是找出会改变正确性、安全性、兼容性、运行稳定性和可审查性的真实风险。

## 建立审查基线

开始前确认：

- 被审查的准确 diff、base、head 和当前状态；
- 需求、Issue、验收条件和明确非目标；
- 仓库约定、负责人边界和目标运行环境；
- 本地已有修改是否与审查对象无关；
- CI、测试和报告是否对应当前 head，而不是旧提交。

如果没有明确需求，先从 diff 推断作者声称改变的行为，并将其标为待确认，不能自行补造需求。

## 按真实影响展开代码地图

不要只逐行阅读 diff。先建立：

- 改动文件按职责分组；
- 被修改符号的调用方与被调用方；
- 协议、配置、数据模型和外部入口；
- 测试、部署脚本、迁移和文档；
- 运行时状态、缓存、队列、线程和外部副作用。

对于移动、重命名、签名或协议修改，要搜索全仓引用、动态导入、字符串路径、测试 patch、脚本和仓库外契约。

## 先验证行为，再评价实现

逐项核对：

1. 改动是否解决真实需求，而不是只实现描述中的技术方案？
2. 正常路径的输入、状态变化、输出和副作用是否正确？
3. 边界、失败、超时、重试、取消、重复执行和并发时会发生什么？
4. 上下游契约、数据完整性、权限和运行环境是否一致？
5. 回滚或旧版本共存时是否安全？

详细审查维度读取 [references/review-dimensions.md](references/review-dimensions.md)。只深入与当前 diff 存在真实可达关系的类别，不制造与改动无关的猜测性问题。

## 主动反证

至少尝试一个最可能推翻作者声明的场景，例如：

- 空值、脏输入、最大输入、截断或分页未完成；
- 网络超时、部分成功、重试和重复投递；
- 两个请求同时修改共享状态；
- 进程在写入或外部副作用之间重启；
- 非法身份、跨用户标识或注入输入；
- 旧数据、旧配置或旧版本程序与新版本共存；
- 测试 patch 指向旧依赖位置，因此什么也没测到。

不能因为存在测试或 CI 绿色就跳过反证。

## 验证证据

按风险从窄到宽验证：

- 阅读调用方、实现、测试、配置和部署路径；
- 运行最小复现或相关专项测试；
- 对共享契约、入口、迁移和基础设施改动运行更广回归；
- 检查测试是否执行到目标路径，断言是否验证正确性及副作用；
- 区分本次引入失败、基线失败、环境差异和 flaky；
- 未运行的检查不得写成通过。

审查请求默认只授权读取和验证。未经用户明确授权，不提交、推送、评论、审批、合并或修改代码。

## 形成可操作 finding

只报告满足以下条件的问题：

- 与当前 diff 存在真实因果关系；
- 能描述具体触发条件；
- 能说明用户或系统影响；
- 有代码、调用链、配置或实验依据；
- reviewer 可以据此采取明确动作。

每条 finding 包含：

- 严重级别；
- 简短标题；
- 最小必要的文件和行号；
- 触发场景与影响；
- 为什么现有测试或保护不足；
- 最小修复方向，不替作者扩大设计范围。

严重级别和输出格式读取 [references/finding-and-verdict.md](references/finding-and-verdict.md)。

## 最终判断

先输出 findings，按严重程度排序；没有 finding 时明确说明未发现阻塞问题，同时列出未验证范围和残余风险。

最终结论只能是基于当前证据的：

- 可合并；
- 修复非阻塞问题后合并；
- 保持 Draft/暂不合并；
- 信息不足，需先完成指定验证。

不要用“整体不错”弱化阻塞项，也不要把样式偏好、无证据防御建议或与当前改动无关的历史问题冒充 finding。
